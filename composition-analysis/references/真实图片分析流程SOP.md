# 真实图片分析流程 SOP（v1 / 2026-11-12）

> 目的：把 **21 类构图结构**用作命名，把 **Pinterest 参考图库**用作视觉参照，最终产出对用户真实图片的分析结果。
> 图库和分类是手段，不是交付物本身。
> 本轮不改网页代码、不改识别阈值、不恢复拍摄角度自动输出。

---

## 一、输入要求

### 1.1 需要用户提供的图

| 项 | 要求 | 说明 |
|---|---|---|
| 图片文件 | 原图或清晰副本，JPG / PNG / WEBP 均可 | 建议短边 ≥ 800px；过小无法核对表盘、边缘裁切、前中后景 |
| 数量 | 单轮 3–8 张 | 小批量便于逐张细读，也便于横向比较 |
| 题材 | 说明每张是什么（人像 / 商品图 / 上手图 / 场景图等） | 题材与构图结构分开记录，不由题材推构图 |
| 用途 | 说明准备用在什么地方（封面、商品主图、详情页、朋友圈、投放素材等） | 有多张图时才做「哪张更适合」的比较；没给用途就只做条件性比较，不替用户定用途 |
| 已知信息 | 是否需要突出某个商品、是否要留压字空间、横版还是竖版投放 | 影响适配结论，不影响构图判定 |

### 1.2 当前项目的真实图片现状（必须如实说明）

- 项目根目录**没有本轮新上传的、等待分析的图片**。
- 项目内存在**历史真实拍摄图库**：`构图工具/_dev/_val300`（真人照）、`构图工具/_dev/_sample_sku`（SKU / 腕表 / 实物图）。它们是真实图片，**不是 Pinterest 参考图，也不是合成 fixture**。
- 第一轮试做使用了其中 4 张，属于「用历史真实图片跑通流程」，**不等于分析了用户这次想分析的图**。
- 若用户要分析自己的图，请把图片放进工作区并说明用途；流程不变，直接替换输入即可。
- **严禁用 Pinterest 参考图代替真实图片做试跑**，那只会验证图库自身。

## 二、四层标签必须分开

| 层 | 内容 | 取值来源 | 能否自动 |
|---|---|---|---|
| 构图结构 | 21 类主构图 + 辅助结构 + 开放／封闭 + 主体关系 | 画面本身 | 人工判读；网页 `TAX` 仅 17 类 |
| 题材 | 手表产品图 / 手表上手图 / 服饰人像 / 生活方式人像 / 宠物 / 静物／食品 / 建筑／室内 / 风景／旅行 | 画面本身或用户说明 | 人工 |
| 拍摄属性 | 景别、拍摄角度、横竖版、主体数量 | 画面本身 | **拍摄角度自动识别已停用**，只写「未标注」；景别是人工参考标签 |
| 设计版式 | 海报 / 杂志封面 / 图文排版 / 产品对比图 / 教程示意图 / 网格图 / 多图拼贴 / 非版式／实拍 | 画面本身 | 人工 |

**硬规则**：不从「平铺构图」反推相机是垂直俯拍；不从「透视汇聚／仰视汇聚」反推仰拍；不从画面明暗反推光源方向并当作角度证据。

## 三、判读七步

1. **先看整幅，不做分类**：确认是单幅实拍、多图拼贴、海报版式还是教程示意图。版式图先记版式标签，构图判定要额外说明是否受版式影响。
2. **用判断卡做减法**：逐条看 `21类构图判断卡.md` 里的「不能判成这一类的情况」，把明显不成立的类别先划掉。这一步比找正例更重要。
3. **找主构图**：在剩下的类别里，看「画面中需要看到的判断证据」是否齐备，选**画面证据最强、能解释整体组织方式**的那一类，不是选「感觉最像」的那一类。
4. **列辅助结构**：可以有多个。写清楚每个辅助结构由哪条线、哪块空域、哪组元素支持。
5. **落到具体位置**：主体框的坐标范围（占画幅百分比）、面积占比、引导线的起点与终点、留白在哪一侧、前中后景各是什么、视觉重量靠什么平衡。
6. **处理不确定**：类别重叠时写清「若按 A 解读则…、若按 B 解读则…」，并给出倾向与理由；证据不足时直接写「不确定 / 不判」，**不为了凑满 21 类硬判**。
7. **做案例对照**：从图库挑 1–3 张，按画面写相似点与不同点，保留编号和来源类型；对照图可以来自不同题材，但必须说明差异。

## 四、单张图输出模板

```
【代号｜说明｜原始路径｜像素】
一、主构图：X（把握度：高／中／低）
   判断证据：……
二、辅助结构：A、B、C（各写由什么画面元素支持）
三、画面位置
   主体位置与占比：x __–__% / y __–__%，约占画面 __%
   引导线：从 __ 到 __，是否指向主体
   留白：位于 __，是否连续、是否被硬线切开
   前中后景：前 __ / 中 __ / 后 __
   视觉平衡：靠 __ 取得，居中／镜像／配重
四、不确定与排除
   重叠：……（倾向与理由）
   排除：不是 X（原因）、不是 Y（原因）
五、分层标签
   题材：…｜景别（人工参考）：…｜拍摄角度（人工参考）：未标注
   横竖版：…｜主体数量：…｜设计版式：…｜开放／封闭：…｜主体关系：…
六、图库案例对照（1–3 张）
   #编号｜主构图｜来源类型｜对照角色
   相似：…
   不同：…
七、原图 / 标注图 / 案例图文件位置
```

## 五、多张图的用途适配比较

- 用户**给了用途**：只按该用途比较，说明「哪张更适合 + 为什么」，并指出其它图在该用途下的具体短板。
- 用户**没给用途**：明确写「未指定用途，以下为条件性比较」，最多列 2–3 种常见用途（如商品主图、封面／压标题图、氛围配图），每种各自给结论，**不要合并成一个总排名**。
- 比较依据必须是画面事实：主体占比、商品可辨识度、可压字的连续空域、边缘裁切、背景干扰、横竖版匹配；不要用「更高级」「更有质感」这类无法核对的判断。

## 六、案例来源口径

- 图库共 133 张：**11 张单 Pin 页**精确链接（`pinterest.com/pin/<id>/`）；**122 张 ideas 主题集合页**来源（`pinterest.com/ideas/<slug>/<id>/`）。
- 主题集合页**只说明该图出现在这个主题集合里，不是这张图自己的原始 Pin 页**；Pinterest 对未登录访问者不暴露集合页中每张图的单 Pin ID，索引里明确写「页面未暴露（未登录 SEO 页）」，不虚构。
- 索引里的「来源标题(仅溯源)」只用于追查图片出处，**不作为分类依据**。
- 分类依据只能是画面本身。

---

## 七、五条硬边界

1. **知识库里有这个类别 ≠ 网页已经能自动识别**：网页 `compose-engine.js` 的 `TAX` 仍为 17 类；第 18–21 类网页「未支持（仅视觉参考）」。
2. **参考图数量、类别数量都不能当识别准确率**：每类几张只说明视觉案例覆盖，不能推出任何百分比准确率。
3. **视觉案例增加 ≠ 网页自动识别新增类别**。
4. **拍摄角度自动识别已停用**：不得因本流程恢复网页的仰拍／鸟瞰／平视输出；角度只作人工参考标签。
5. **本流程是人工判读 SOP，不是网页引擎的验收报告**：网页输出是否正确需要单独跑网页 JS 验证，两套结果不能混用。
